# AI 电台延迟治理 —— 三个解决方案（附实测依据）

日期：2026-09-21
背景：辛老师反馈「有时候太慢了，或者会卡壳」。上一轮（`45d291c`）已把手机端
「点击 → 出声」从 35s 压到 3.7s（4G），本次针对**剩下的延迟**给出可选方案。

所有数字都是实测，不是估算。测量环境：本地后端 COS 模式（复刻线上曲库来源）+
playwright-core 驱动 Chrome 152，网络用 CDP 限速、CPU 4× 降频。

---

## 一、先定因：延迟的物理公式

> **起播时间 ≈ Chrome 起播预读量 ÷ 有效带宽**
> Chrome 起播前固定预读约 **60 秒音频**，与 `preload` 设成 auto / metadata / none **完全无关**
> （实测 13300 / 12876 / 13058 ms，三者一致）。

因此真正能被优化的只有一个变量：**码率**。

### 曲库实测（107 首全量体积 + 14 首均匀采样读元数据）

| 指标 | 实测值 |
|---|---|
| 总量 | **1113 MB** / 107 首 |
| 平均码率 | **337 kbps**（中位 335，区间 322–364） |
| 码率 > 256 kbps 占比 | **100%**（几乎全是 V0/VBR320 级） |
| Chrome 起播预读 60s 对应体积 | **2.41 MB / 首** |

### 起播耗时推算 vs 实测

| 网络 | 公式推算 | 实测 |
|---|---|---|
| 4G 8 Mbps | 2.4s | 单元素 canplay **2.98s** ✅ |
| Slow 4G 1.6 Mbps | 12.0s | 上一轮实测 **13.4s** ✅ |

公式站得住，可以拿来预测方案收益。

## 二、「卡壳」的成因拆解（隔离实验，空白页零 App 代码）

同一首歌、同一限速（8 Mbps），只改「有没有第二个媒体在抢」：

| 场景 | music canplay | 差值 |
|---|---|---|
| A 单个元素 | 2976 ms | — |
| B + 同时下载**另一整首**（3.68 MB） | 4786 ms | **+1810 ms** |
| C + 同时下载 **128 KB** | 3191 ms | +215 ms |
| D + **正在播放**的 128 KB 小音频 | 5163 ms | **+2187 ms** |

结论：
1. **「DJ 语音抢音乐带宽」的猜想被证伪** —— DJ 语音实际只有 ~110 KB，
   纯下载代价仅 +215 ms。真正贵的是「有媒体元素在播放」这件事本身（+2.2s），
   属于 Chrome 媒体加载调度，不是字节数。
2. 单次并发代价量级是 **2 秒级**，不是十几秒级。所以如果真机上出现十几秒空窗，
   那是 **App 内部特有的问题**，需要单独查（见下）。

### App 内实测（同条件，走完整前端）

| 时刻 | 事件 |
|---|---|
| 2766 ms | music 元素被设 src（页面加载即设，`preload=metadata`） |
| 3088 ms | 用户点击「开始电台」→ 调 `/api/dj/open` |
| 5514 ms | DJ 开场白音频开始播放（13.6 s 长） |
| 6181 ms | music 触发 `stalled`，`readyState=0` —— **音乐下载停滞** |
| 19248 ms | DJ 开场白说完 |
| 22564 ms | music 才 `canplay`（缓冲 61s） |
| — | **点击 → 出声 22957 ms** |

DJ 语音结束后音乐才恢复加载 —— 而隔离实验证明 128 KB 并发只值 0.2~2.2 秒，
**解释不了这 16 秒**。结论：`preload=metadata` 下「点击前就 set src」很可能让 Chrome
把该元素放到惰性队列，之后 `play()` 又得重新排队。这是可被方案 ② 直接绕开的。

### 另外两项确定的等待

| 项目 | 实测 | 说明 |
|---|---|---|
| 切歌 gap | `/api/skip` 80 ms + 新曲 canplay 3.3 s ≈ **3.4 s** | 未命中预取时（进度 <85%）走真实下载 |
| DJ 开场/串场 | `/api/dj/open` **5.0 s** | LLM 写稿 + TTS 现做；这 5 秒前端无反馈 → 「卡壳」主观来源 |

## 三、三个解决方案

### 方案 ① 音频转码为双档位（根治带宽，需密钥）

**做法**：ffmpeg 批量转 **AAC-LC 128 kbps**，与原档并存；manifest 增加 `urlLow`；
前端按 `navigator.connection.effectiveType` / `saveData` 选档，WiFi 仍走原档。

| 指标 | 现在 | 转 128 kbps |
|---|---|---|
| 首包（60s 音频） | 2.41 MB | **0.96 MB** |
| 全库体积 | 1113 MB | **≈ 423 MB（−62%）** |
| 起播 4G / 3G / Slow4G | 2.4 / 6.4 / 12.0 s | **0.9 / 2.4 / 4.6 s** |
| 切歌 gap | 3.4 s | ≈ 1.3 s |

- 收益最大、全场景生效；**双档位设计可做到零音质损失**（好网络仍听原档）。
- 代价：需腾讯云密钥；上传约 420 MB；新歌入库增加一步转码。
- 风险：128 kbps 在好耳机上可辨；如介意可改 192 kbps（首包 1.37 MB）。

### 方案 ② 把等待挪到点击之前，并绕开 Chrome 媒体调度（纯前端，零成本）

**现状问题**：点击前只 set src 不下载（`preload=metadata`），点击后才真下；
且真机实测出现 16 秒媒体加载停滞。

**做法**：
1. 页面加载后**不要提前 set src**（别惊动媒体加载器）；
2. 改用 `fetch` 把当前歌**整首下成 Blob**（`audioCache` 链路已实现并验证过：
   blob 播放与直链音质/analyser 完全一致），点击 → 直接播 blob，**起播 ≈ 0.2 s**；
3. 用户读引导页的时间正好用来下载（裸 fetch 实测 880 KB/s，2.41 MB 只需 2.8 s）；
4. Blob 未就绪时自动降级为原流式起播，**不劣化**；
5. 预取阈值从 85% 提前到 50%，给慢网留足余量。

- 收益：起播几乎归零，且**不需要密钥、不需要重传**；今天就能上。
- 代价：多占一点内存（每首约 3–10 MB，已有 LRU 淘汰，最多留 2 首）。
- 注意：仅对「页面停留超过下载时间」有效；秒点秒进时降级为原体验。

### 方案 ③ DJ 语音预热，消灭「音乐停了等人说话」（服务端小改）

**现状**：`/api/dj/open` 要 5.0 s 才出声（LLM 写稿 + TTS 合成），切歌串场同样现做。

**做法**：
1. 服务启动 / 首次访问即**预热开场白**并落盘缓存；
2. 串场改为**提前一首生成**：播到 70% 时生成下一首的串场稿 + TTS，缓存（相同文案 hash 复用）；
3. WS 下发时若命中缓存 → 直接给音频地址，前端 0 等待。

- 收益：点击后 DJ 立刻开口；切歌时音乐与 DJ 几乎同时起，主观「卡壳」基本消失。
- 依赖：无（LLM 已具备 DeepSeek 故障切换，TTS 走 MiMo / Edge 兜底）。
- 代价：预热会消耗少量 LLM/TTS 额度（可忽略）。

### 附：第 4 个杠杆（非代码）

Render 免费版 **0.1 核 CPU** 是硬伤，多端同时在线会互相抢。升到 Starter（约 $7/月）
换成 0.5 核 + 常驻不休眠，可一并消除冷启动与并发卡顿。

---

## 四、建议执行顺序

1. **方案 ② + ③ 一起做**（零成本、纯代码，覆盖「起播慢」和「卡壳」两个主观痛点）；
2. **方案 ① 等密钥**，一次性成本换全场景 2.5 倍提速，且能顺带把 1113 MB 压到 423 MB；
3. 若多端并发仍卡，再考虑升实例。

## 五、本次顺带发现的小问题

- 停止播放 / 切歌清理时，媒体元素被赋 `src = ""`，浏览器会解析成文档 URL
  并触发 `error` 事件（实测 `ev:error ... src=http://127.0.0.1:8787/`）。
  不影响播放，但污染日志、可能误触错误处理。建议改为
  `removeAttribute('src')` + `load()`。

### 测量坑（沿用上一轮教训，写进脚本注释）

1. `new Audio()` 是**游离元素**，`document.querySelector` 看不见 → 必须劫持
   `HTMLMediaElement.prototype`（play / load / src setter）建注册表；
2. 限速表**漏档会静默回落**（`NETMAP` 里写 `fourg` 却只有 `slow4g`）→ 现在缺档直接报错退出；
3. 覆盖 `src` 的 getter 时若回头再调 `getOwnPropertyDescriptor`，会**无限递归爆栈**
   （已踩）→ 先把原 getter 存变量；
4. `addInitScript` 只对**之后的导航**生效，`page.goto('about:blank')` 之后再注入等于没注入
   → 必须再 go 一次（已踩）。
