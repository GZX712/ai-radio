# 客人路径全面排查报告（2026-09-25）

> 问题：「客人浏览的时候会不会出现（完全无声）这种情况？全面排查 bug」
> 方法：通读客人完整链路全部代码（播放引擎 / 手势流 / 音效 / 缓存 / WS / 服务端放行策略）
> + 探针实证。结论先行：**客人不会踩上「完全无声」那个坑**（有「开始电台」手势 +
> 9/25 的延迟接线修复双保险），但排查出 **5 个真实 bug 已修** + **4 个待拍板项**。

## 一、直接回答：客人会不会完全无声？

**不会（同机制）。** 三条防线：

1. 客人有「▶ 开始电台」按钮 = 同步手势，`unlock()` 在手势栈里发起 resume —— 主人设备踩的
   「页面上没有任何手势入口」这个前提在客人路径不存在。
2. 即使 unlock 失败（微信 X5 等怪环境），9/25 的延迟接线修复保证元素**不接线走默认输出，
   至少有声音**；且「轻触开启声音」提示条同样对客人生效（探针 locked 模式实测：提示条出现、
   进度 0.64→12.69s 不卡死）。
3. 4 处 `await ctx.resume()` 已全部改 fire-and-forget，播放流程不存在被 resume 卡死的路径。

## 三、探针实证的设计缺陷（未改，待拍板）

1. **客人欢迎词时机错位（已录到证据）**：新客人的 WS 一连接就触发 `fireGuestGreeting`，
   此时客人还没点「开始电台」= 无手势 → 探针实测客人侧 `play:fail NotAllowedError` ×2，
   **客人自己永远听不到对自己的欢迎词**，只有在听的主人设备听得到。且任何随机 WS 连接
   （含爬虫带随机 deviceId）都会白烧一次 LLM+TTS。
   建议：改为「客人首次点击开始电台后」再触发欢迎（前端把手势事件通知后端，或干脆去掉
   新客隆重欢迎只留 10 分钟低调问候）。
2. **CLAIM_TOKEN / OWNER_SECRET 默认值硬编码**，且口令就在前端 bundle 里
   （`xradio-master-2026`）→ 任何看源码的客人都能把自己绑成主人 → 可改全站 DJ 音色、
   写主人云端档案（壁纸/头像跨设备同步）。
   建议：Render 上设置 `EGG_OWNER_TOKEN` + `EGG_OWNER_SECRET` 新值 → 旧 bond 全部失效 →
   两台主人设备用新口令 `/?claim=<新口令>` 重新绑一次（1 分钟操作）。需要我改代码把客户端
   里的默认口令删掉的话说一声。
3. **客人能切歌/点歌（共享队列）**：`/api/skip|next|prev` 与点歌广播无门禁，且每个客户端的
   看门狗 stall 也会 autoSkip 推进**全局**队列 —— 客人网络抖动会替主人跳歌，DJ 还会向所有人
   播报「下一首」但各端本地放的还是旧歌（对不上）。
   这是「电台=共享队列」的设计使然，改不改是产品决策。我的建议：队列推进类接口改主人专属
   （客人只收听+聊天），客人的本地 stall 只重试本地播放不推全局队列。
4. **客人也整首预取下一首**（10MB 量级）→ COS 按流量计费的成本随客人数线性涨。
   建议：客人设备跳过音频预取（保留封面预热），或保留现状接受成本。

## 四、顺带澄清（排查中确认无问题）

- audioCache blob 生命周期：pin 保护正在播的、revoke 不误伤、并发去重 —— 健康。
- sfx 第二个 AudioContext：入场/切歌音效都在用户手势内触发，`getCtx()` 每次调用都尝试
  resume —— 客人可用；非手势场景（罐头笑）用普通 Audio 元素，autoplay 被拒时静默，不炸。
- laugh 罐头笑：尊重音效开关 + 6s 冷却 + 静默兜底 —— 健康。
- 续播记忆（resume）：客人各自独立 localStorage，互不影响 —— 符合设计。
- 聊天记录：客人启动即清本机残留，服务端不注入跨设备记忆 —— 符合设计。
